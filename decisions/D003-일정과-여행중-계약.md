## 최소 데이터 관계와 불변 조건

아래는 논리 계약이다. SQL/마이그레이션·공급자 응답 스키마는 만들지 않았다. 별도 여행 삭제·보관함·휴지통은 범위 밖이다.

| 개념 | 최소 책임과 값 | 관계·검증 |
| --- | --- | --- |
| 계정 | 인증 사용자 식별자, 서버 관리 등급, 별도 관리자 권한 | 클라이언트가 소유자·등급·관리 권한을 지정/변경할 수 없음 |
| 여행 | 안정 ID, 소유자, 이름, 날짜별 계획, 변경 revision | 한 소유자에 속하며 다른 계정의 자식 데이터 접근도 차단 |
| 여행 날짜 | 안정 ID, 여행 ID, 달력 날짜 | 같은 여행에서 같은 날짜 중복 불가. 날짜 개별 추가(Q01); 시작/종료 범위로 자동 생성하지 않음. 날짜 삭제 기능은 이번 구현 범위에 추가하지 않음 |
| 저장 장소 | 안정 ID, 여행 ID, 장소명, 위치 정보, 선택 메모·분류 | 위치 값은 검색 획득값 재입력 없이 사용. 실제 출처/응답/보존은 T02 대기 |
| 일정 배치 | 안정 ID, 날짜 ID, 장소 참조, 명시 순서, 선택 예정 시각·메모 | 같은 여행의 날짜/장소만 참조. 반복 배치 허용·장소 공통 메모와 배치별 메모 구분은 Q01 |
| 이동 구간 | 출발/도착 일정 배치 ID, 수단·저장 교통 정보 | 장소 ID만으로 반복 방문 구간을 식별하지 않음. 후보 1개·인접 배치 쌍별 보존은 Q07 |
| 등급 정책 | 무료/유료1/유료2별 여행·장소 한도, 정책 revision | D001 초기값 3/50, 15/150, 50/300. 관리자만 변경 |
| 기기 사본 | 사용자 ID, 여행 ID, 서버 revision, 수신 시각, 사본 형식 버전, 허용된 계획 내용 | 인증 토큰·GPS 궤적·공급자 비밀 키를 계획 사본에 포함하지 않음 |

여행·날짜·장소·배치의 ID는 순서 변경과 이름 변경으로 바뀌지 않는다. 날짜/장소/구간을 다른 여행에 잘못 연결하는 쓰기는 서버에서 거부한다. 변경된 일정 순서와 구간을 따로 성공 처리해 혼합 상태를 만들지 않는다. 한도는 저장 장소 수와 일정 배치 횟수를 구분한다.

이름·날짜 등 실제 필수 입력은 해당 개념 식별에 필요한 값만 둔다. 비용·예약 상태·방문 완료·체류 종료 시각 등 새 필드를 도입하지 않는다. 날짜 변경으로 기존 배치가 사라지는 동작을 암묵적으로 넣지 않는다.

## 시간 판단 계약

공통 확정: 기기 시각과 저장된 계획으로 **예정**을 판단하며 실제 방문·지연을 알 수 없다. 시각 없는 일정도 허용한다. 다른 날짜의 마지막 장소를 오늘 현재 장소로 자동 이월하지 않는다. 시간대·동일 시각·마지막 이후 규칙은 승인된 Q03과 아래 표를 따른다.

Q03 확정 알고리즘: 초기 한국 여행은 `Asia/Seoul`로 판단하고 예정 시각은 해당 날짜의 분 단위 시각으로 둔다. 날짜 내 표시/방문 순서는 사용자가 정한 순서다. 시각이 역순이면 저장 전 안내하고 사용자가 시각 또는 순서를 수정한다. 임의 시간 정렬이나 자동 시간 보정은 하지 않는다. 시각 없는 항목은 순서에는 남고 자동 현재/다음 판단에서는 제외한다. 시각이 있는 항목의 직전 시작 시각부터 다음 시작 시각 전까지 현재 예정으로 본다. 종료 시각·완료 버튼은 추가하지 않는다.

| 조건 | Q03 확정 결과 | 의미/경계 |
| --- | --- | --- |
| 10:00 A, 11:00 B / 지금 09:59 | 현재 없음, 다음 A | 여행 시작 전 |
| 같은 자료 / 10:00 또는 10:59 | 현재 예정 A, 다음 B | 시작 포함, 다음 시작 전까지 |
| A 10:00, B 10:00, C 11:00 / 10:00 | 같은 시각 A/B를 한 묶음으로 표시, 다음 C | 임의로 한 장소만 현재로 고르지 않음 |
| A 10:00, X 시각 없음, B 11:00 / 10:30 | 현재 A, 다음 B; X는 전체 일정에 남음 | X를 방문 완료나 자동 건너뛴 장소로 해석하지 않음 |
| 마지막 시각 이후, 같은 날짜 | 마지막 장소를 마지막 예정으로 표시, 다음 없음 | 완료·현재 GPS 위치라는 뜻 아님 |
| 오늘 일정 없거나 모든 시각 없음 | 자동 판단 불가, 날짜별 전체 일정 확인 | 가짜 현재/다음 없음 |
| 자정 | 새 날짜 기준으로 다시 판단 | 전날 현재 장소 자동 유지 안 함 |
| 계획보다 실제 행동이 늦음 | 계획 판단 유지, 임의 목적지 선택 가능 | 자동 지연 보정·방문 추적 없음 |
| 기기 시각 오류 | 잘못된 기기 시각이면 잘못된 결과 가능 | 서버 방문 사실로 표시하지 않음; 기기 시각 기반임을 구분 |

해외 시간대·자정 넘는 단일 일정·종료 시각은 기존 입력에 없으므로 이번 계약에 추가하지 않는다. 해외 지원은 별도 사용자 결정이 필요하다.

## 인증·서버 저장·기기 사본 공통 계약

- 온라인 여부만으로 수정 허용을 판단하지 않는다. 서버가 현재 사용자 인증·소유권을 검증해야 쓰기가 성공한다. 인증 만료·서버 중단·네트워크 실패를 저장 성공으로 표시하지 않는다.
- 서버 원본 조회는 일관된 여행 revision과 내용으로 받는다. 다른 기기의 변경이 자동 실시간 반영된다고 보장하지 않는다. 조회 시점과 충돌 UX는 Q05.
- 서버 저장 성공과 IndexedDB 갱신 성공을 구분한다. 서버 저장은 성공했으나 사본 저장 실패 시 서버 성공은 유지하고 오프라인 준비 미완료를 표시한다.
- 사본은 완전한 여행 revision 단위로 교체한다. 중간 다운로드/저장 실패 시 새 내용 일부와 옛 내용 일부를 섞지 않는다. 기존 완전본이 있으면 그 revision·수신 시각을 표시한다.
- 사본은 계정·여행별로 격리한다. 계정 전환 중 이전 계정 내용이 화면·메모리·IndexedDB 조회 결과로 노출되지 않아야 한다. 접근/삭제의 사용자 정책은 Q04.
- 오프라인 쓰기·저장 대기열·자동 재전송·자동 병합은 없다. 온라인 편집 도중 연결이 끊기면 미저장 상태로 두고 서버 성공을 확인하기 전 다른 기기 이용 가능으로 표시하지 않는다.
- 저장 응답을 못 받은 요청은 성공/실패가 불명확하다. 자동 재전송으로 중복 여행·장소를 만들지 않고 최신 서버본을 다시 확인한 뒤 결과를 판단한다.
- 앱 자원 준비와 여행 사본 준비는 별개다. 최초 로그인·미준비 여행은 오프라인에서 열 수 없다. 브라우저 삭제/용량 부족·origin 변경은 준비 상태를 잃을 수 있으며 사본은 백업이 아니다.
- 현재 `vite.config.ts`의 정적 자원 캐시를 인증 API·여행 API·지도 API 캐시로 확대하지 않는다.

## 동시 수정·한도·관리자 공통 계약

서버 쓰기는 인증, 소유권, 입력 관계, revision, 한도 판정을 하나의 원자적 성공/실패로 처리한다. 직결 테이블 쓰기나 별도 함수로 이 검증을 우회할 수 없어야 한다. 클라이언트 전달 소유자·등급·개수·한도·관리자 플래그를 신뢰하지 않는다. 구현 시 RLS와 쓰기 함수 권한을 함께 검증한다.

한도 검사는 서버 현재 등급/정책으로 수행하고 동시 생성 요청을 직렬화해야 한다. 여행 수는 계정 단위, 장소 수는 여행 단위로 경쟁을 제어한다. 등급·정책 변경과 생성의 경합은 일관된 순서로 판정하고 교착을 피하는 잠금 순서를 구현 계약에 남긴다. 정책 변경 커밋 후 다음 쓰기부터 최신 한도를 적용한다(Q06). 정책 조회와 데이터 쓰기를 따로 수행해 오래된 한도로 생성하는 경로를 허용하지 않는다.

관리자는 등급별 두 한도의 조회·변경만 수행한다. 관리자 권한과 사용자 등급은 별개다. 유료2라는 이유로 관리 권한을 주지 않는다. 한도는 유한 양의 정수이며 무제한·0을 뜻하는 특수 값을 사용하지 않는다. 정책 변경에도 revision 검사를 적용해 두 관리자의 설정을 조용히 덮어쓰지 않는 방식은 Q05 계약에 포함한다.

신규 무료 등급, 운영자의 서버 관리 절차, 유료 등급 변경과 초과 보존은 Q06으로 확정됐다. 실제 관리자 대상 사용자 ID는 후속 실제 설정 시 지정·검증하며 정책 확정을 차단하지 않는다. 관리자 사용자 관리 화면·결제·유료 인프라 설정은 이번 계약에 포함하지 않는다.

## 위치·주변 목록·이동 경계

GPS는 사용자가 해당 기능을 사용할 때 허용 요청하며 궤적 장기 기록을 하지 않는다. 거부·실패·확보 중에는 위치가 있다고 가장하지 않고 저장 일정·장소는 계속 확인하게 한다. 새 위치를 얻지 못한 상태에서 과거 위치를 현재 위치로 표시하지 않는다. 좌표만 있고 위치 확보 시각/정확도를 잃지 않도록 실제 구현에서 표시한다. 실제 GPS/권한 동작은 T09/T12 검증 대상이다.

주변 조회 대상·분류는 Q02, 직선 거리와 이동 거리/시간 구분은 공통 계약이다. 위치가 없으면 거리와 가까운 순서 판단은 제공하지 않는다. 임의 반경·새 주변 업소 검색·위치 추적을 추가하지 않는다.

이동은 일정 배치의 인접 관계를 기준으로 한다. 순서·장소 변경 뒤 옛 출발/도착에 해당하는 정보를 새 구간으로 자동 복사하지 않는다. 현재 GPS 출발 길찾기와 계획의 장소 간 구간은 다르다. 후보 수·구간 삭제/보존은 Q07, 공급자 조회/저장/출처·지도 표현·외부 링크는 T02 이후 계약이다.

### 구현에 필요한 관계·동시성 세부 계약

- 같은 저장 장소를 재배치할 때 기존 장소 ID를 참조한다. 장소명·주소가 비슷하다는 이유로 자동 병합하지 않는다. 공급자 장소 식별자 기반 중복 매핑은 T02 이후 확정한다.
- 예정 시각은 날짜와 결합된 분 단위 시각(00:00–23:59) 또는 미지정이다. 표시 순서의 시각 지정 항목은 비감소여야 한다. 동일 시각 묶음 내부 순서는 사용자 배치 순서를 유지한다. 마지막 묶음도 여러 장소라면 함께 마지막 예정으로 표시한다.
- 순서 값은 날짜 안에서 유일하고 서버 저장 후 전체 순서가 확정돼야 한다. 장소 수정·배치 삭제·재정렬과 영향을 받는 구간은 동일 여행 revision 쓰기로 적용한다. 장소명/메모 수정만으로 인접 배치 쌍이 바뀌지 않으면 구간 정보는 유지한다. 배치의 장소 참조를 다른 장소로 변경하면 출발/도착이 바뀐 관련 구간 정보는 유지하지 않는다.
- 여행 쓰기는 읽은 revision을 보내고 서버가 동일할 때만 변경 후 revision을 증가시킨다. 서로 다른 날짜/장소를 수정해도 같은 여행이면 충돌한다. 최신 조회 성공 시에도 미저장 편집을 자동 교체하지 않고 최신본 확인·재편집을 안내한다. 정책 revision은 여행 revision과 별도로 검사한다.
- 서버 쓰기의 잠금 책임은 정책 → 대상 계정의 등급/여행 수 → 여행 revision/장소 수 순서로 통일한다. 필요한 잠금만 사용하되 한도 변경·등급 변경·생성의 같은 자원 경쟁은 동일 순서를 따른다. 정책 변경과 경합한 쓰기는 이 순서에 의해 변경 전 또는 후 한도로 원자적으로 결정되며 부분 적용되지 않는다. SQL/함수 구현은 T05 책임이다.
- 한도 하향 이후 초과 상태에서 이름·날짜·메모·분류·시각·순서 수정, 기존 장소 재배치와 삭제는 개수 증가가 없으면 허용한다. 새로운 여행/장소 추가는 해당 한도 판정으로 거부한다. 여행 수 초과가 장소 수 불변 편집 전체를 막지 않는다.
- 기존 구간을 삭제하는 편집에서 안내를 취소하면 저장하지 않는다. 승인한 경우 편집·구간 삭제를 한 번에 저장하며 충돌/실패 시 서버 기존 구간을 유지한다. 날짜 경계를 넘는 구간 생성은 이번 계약에 추가하지 않는다.

## 검증 기록

최신 main/브랜치/열린 PR, 기준 문서, 실제 App/PWA 파일을 읽었다. 사용자 승인 Q01–Q07과 위 사례를 수동 대조하고 조건부/승인 대기 표현을 확정 계약으로 갱신했다. 문서 링크·요구 ID·선행 조건·diff 검증 결과는 CURRENT_STATE에 기록한다. 코드·SQL·테스트·패키지·설정은 변경하지 않았으며 빌드·실제 인증/DB·기기/지도 검증은 수행하지 않았다.
