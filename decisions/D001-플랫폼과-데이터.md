## 사용자 확정 근거

T01 선택 논의에서 사용자는 다음을 확정했다.

1. 반응형 웹/PWA, React + TypeScript + Vite. 최초 실제 휴대폰은 Android.
2. 로그인 후 서버에 저장하고 PC·휴대폰에서 같은 계정의 계획을 이용.
3. 온라인 로그인 상태에서만 수정. 오프라인은 저장된 내용 확인만 가능.
4. 이용자 등급은 무료·유료1·유료2. 여행 수와 여행 내 장소 수를 제한하고 관리자 페이지에서 한도를 변경.
5. 아래 초기 한도와 초기 검증용 Supabase Free + Google 로그인을 제안한 뒤 사용자가 진행을 승인했다. 실제 서비스 운영은 T13에서 재검토.

사용자 등급은 앱의 이용 정책이며 Supabase의 Free/Pro 요금제와 별개다. 유료 등급 이름이 실제 결제·판매 개시 승인을 뜻하지 않는다.

## 대안 비교와 선택 이유

| 대안 | PC→휴대폰 흐름 | 부담과 제약 | 판단 |
| --- | --- | --- | --- |
| 반응형 웹/PWA + 서버 저장 | 같은 URL에서 로그인해 같은 여행을 열기 | 인증·서버 저장 필요. 휴대폰에서는 화면과 계획을 미리 저장해야 오프라인 열람 가능 | 선택. 한 클라이언트로 PC 편집과 Android 여행 중 이용을 연결 |
| 웹/PWA + 파일 전달 | PC 내보내기→파일 전달→휴대폰 가져오기 | 계정·데이터 서버는 불필요하지만 변경 때마다 재전달 필요 | 미선택. 사용자 로그인·서버 저장 선호와 다름 |
| PC 웹 + 네이티브 Android | 두 클라이언트가 같은 서버에 접근 | 웹·Android UI, 설치·배포·검증을 함께 관리 | 미선택. 현재 요구에 별도 네이티브 앱이 필요한 근거 없음 |
| 공통 UI를 네이티브 앱으로 포장 | 웹 계획 기능과 Android 패키지를 함께 유지 | 패키징·기기별 외부 연결 검증 추가 | 미선택. 현 단계에서는 PWA로 검증 |

| 기술/저장 대안 | 판단 |
| --- | --- |
| React + TypeScript + Vite | 선택. 현재의 로그인 후 계획 앱에는 SSR 요구가 없고, 공식 React/Vite 문서에서 제공하는 SPA 구성을 사용 |
| Vue 등 다른 프론트엔드 | 기능상 가능한 대안. 사용자 승인된 React 구성을 채택하며 복수 프레임워크를 도입하지 않음 |
| SSR 중심 프레임워크 | 현재 요구에는 SSR·검색 엔진 공개 페이지가 없음. 필요성이 확인되지 않아 미선택 |
| Supabase Auth + PostgreSQL | 초기 검증용 선택. 인증·서버 DB·사용자별 접근 제어를 관리형으로 구성 |
| 직접 인증·서버·DB 운영 | 통제 범위가 넓지만 운영·인증·백업 책임 증가. 초기 무료 검증 목적에는 미선택 |
| 브라우저 저장만 사용 | 기기 간 같은 데이터 이용을 충족하지 못함. 원본 저장 방식으로 미선택 |
| IndexedDB + Cache Storage | 선택. IndexedDB는 계획 열람 사본, Cache Storage는 앱 화면에 필요한 자체 정적 자원용 |

네이티브 지원이나 SSR을 영구 금지하지 않는다. 현재 범위를 바꿀 근거가 생기면 별도 결정이 필요하다.

## 최소 기술과 서버 책임

- 하나의 반응형 PWA를 React + TypeScript + Vite로 만든다. 별도 Android 프로젝트는 만들지 않는다. PWA 설치는 선택이고 브라우저 이용도 지원한다.
- Google 로그인을 Supabase Auth로 처리한다. 초기 이메일/비밀번호 로그인, 다른 소셜 로그인, 익명 쓰기는 추가하지 않는다.
- 서버 원본은 Supabase PostgreSQL에 저장한다. 브라우저에 공개 가능한 키와 사용자 인증을 이용하고, 사용자 소유 데이터의 접근은 RLS로 제한한다.
- 계획·여행 생성과 장소 추가의 한도는 서버 측에서 적용한다. 클라이언트 화면의 수 제한만으로 끝내지 않는다. 동시에 두 기기에서 생성해도 한도를 우회하지 못해야 한다. DB 트랜잭션/함수·권한 구성의 구체 계약은 T03에서 정한다.
- 관리자의 한도 변경은 서버 권한 검증을 거친다. 일반 사용자는 자신의 등급·한도·관리 권한을 변경할 수 없다. 관리자 페이지는 한도 변경 범위로 제한한다.
- 별도의 상시 실행 커스텀 웹 서버는 현재 저장·인증 요구에 필요하지 않다. 서버 책임이 없다는 뜻은 아니다. 관리형 Auth/DB와 서버 측 쓰기 검증이 백엔드다.
- T02에서 지도 API의 비밀 키 또는 CORS 조건 때문에 프록시가 필요하면 해당 역할만 추가 검토한다. 비밀 키를 Vite 환경 변수로 브라우저에 배포하지 않는다. 런타임·함수 공급자는 필요한 근거가 확인되기 전 확정하지 않는다.
- 버전·패키지 관리자·정확한 코드 경로·PWA 구성 도구는 T04에서 호환성과 당시 공식 요구를 확인해 고정한다. 여행 세부 스키마는 T03 책임이다.

## PC·휴대폰 사용 시나리오

1. PC에서 HTTPS 웹 앱에 Google 계정으로 로그인한다.
2. 여행을 만들고 계획을 수정한다. 서버 저장 성공을 확인한 내용이 다른 기기에서 사용할 원본이다. 실패한 쓰기를 저장 완료로 취급하지 않는다.
3. Android에서 같은 URL·계정으로 로그인해 서버의 여행을 연다. 필요한 앱 화면과 열람용 여행 사본을 기기에 저장한다.
4. 온라인에서는 서버 최신본을 가져와 확인하고 로그인 상태에서 수정할 수 있다. PC가 켜져 있거나 같은 Wi-Fi에 연결돼 있을 필요는 없다.
5. 오프라인에서는 이미 기기에 저장한 여행의 일정·메모·저장된 이동 정보를 확인한다. 현재/다음 예정 판단은 저장된 계획과 기기 시각으로 수행한다. 공급자 데이터의 사본은 T02의 보관 허용 범위 안에서만 저장한다.
6. 오프라인 여행 생성·장소 변경·메모 수정·삭제·변경 대기열은 지원하지 않는다. 재접속 시 오프라인 쓰기를 자동 병합하는 기능도 없다.

이것은 같은 서버 원본을 두 기기에서 이용하는 방식이며, 실시간 공동 편집·백그라운드 동기화까지 뜻하지 않는다. 온라인 최신본 조회 시점, 동시 수정 충돌·저장 성공 표시·사본 갱신 계약은 T03에서 예시로 확정한다.

## 초기 운영 제약과 재검토

- 초기에는 Supabase Free로 검증한다. 공식 가격표 확인 당시 DB 500MB, egress 5GB, 인증 MAU 50,000, 활성 인프라 프로젝트 2개 한도이며 1주일 비활성 시 일시정지된다. 여기서 인프라 프로젝트 수는 앱의 여행 수가 아니다.
- Free의 자동 백업은 포함되지 않는다. 일시정지된 프로젝트는 운영자가 대시보드에서 복구해야 하므로, 장기간 미사용 후 즉시 이용을 보장하지 않는다. 사용자에게 이 제약을 설명한 뒤 초기 검증용 사용 승인을 받았다.
- 휴대폰 실제 접근에는 HTTPS와 안정적인 origin이 필요하다. 호스팅 공급자·도메인·배포 URL·공개 범위는 아직 미선택이다. T04의 기기 확인에 필요한 임시 검증 환경과 T13/T14의 실제 서비스 배포를 구분한다.
- 현재 결제·유료 인프라 계약·비용 지출·공급자 계정 생성은 수행하지 않는다. 앱의 여행/장소 한도가 공급자의 무료 사용량 준수를 보장하는 것은 아니다. 지도 비용도 T02에서 별도 검토한다.
- T13은 비활성 일시정지, 백업·복구, 사용량·비용, 실제 휴대폰 접속, 관리자·한도 계약을 다시 확인한다. 현재 무료 공급자를 실제 서비스 운영으로 자동 확정하지 않는다. 유료 전환 또는 공급자 변경 비용·데이터/인증 이전 영향은 사용자와 결정한다.

| 온라인이나 로그인/서버 인증이 유효하지 않음 | 수정 불가. UI 캐시만으로 서버 쓰기 허용하지 않음 |
| 무료 여행 3개 또는 한 여행 50곳 이후 추가 | 서버 한도 적용 대상. 경계·동시 생성 검증은 T05 |
| 일반 사용자가 한도/등급/관리 권한을 직접 변경 | 서버에서 불허. 관리자 페이지 표시 유무만으로 보호하지 않음 |
| 한도 낮춤·세션 만료·동시 수정 | T03에서 상세 규칙 확정 후 구현. 임의 데이터 삭제·병합 없음 |
| Supabase 비활성 일시정지 | 온라인 이용 제한 가능. 준비된 사본은 기기 저장이 남아 있으면 열람 가능. 초기 검증의 수용된 제약이며 실제 운영은 재검토 |

이는 설계 사례 대조이며 앱 빌드·실제 기기·공급자 연결 테스트가 아니다. 앱 코드·지도 공급자·호스팅·결제는 이번 작업에서 만들거나 확정하지 않는다.
