## 준비와 재개 조건

사용자가 승인한 개발 Supabase 프로젝트 URL과 공개 publishable/anon 키, 활성화된 Google provider와 허용 redirect URL, 테스트용 두 계정 및 PC/Android 실행 환경이 필요하다. 실제 관리자 대상은 사용자가 지정한 계정의 ID/이메일을 직접 대조한 뒤 설정한다. 개인 운영 데이터 대신 승인된 개발 프로젝트와 테스트 여행만 사용한다.

서비스 비밀 키·OAuth client secret·사용자 토큰을 저장소/PR/보고에 넣지 않는다. 공개 설정은 `.env.local`로 제공하고 비밀 운영자 호출은 서버/SQL Editor에서만 수행한다. 계정 생성·유료 설정·호스팅 배포를 임의 실행하지 않는다. 접근이 없다면 부족한 설정과 사용자 실행 절차를 명확히 기록하고 차단을 유지한다.

초기 migration 미적용 DB에는 001→002 순서로 적용한다. 001을 적용했던 DB에는 002만 추가한다. 테이블/사용자 데이터를 삭제하거나 초기 migration을 재실행하지 않는다. provider를 먼저 시험했던 기존 사용자도 프로필이 생성돼 있는지 확인한다. 함수/권한/RLS는 SQL Editor 관리자 권한에서만 시험한 것으로 통과 처리하지 않는다.

## 수행 범위와 검증 사례

1. **실제 인증/HTTP**: Google OAuth PKCE 1회, 같은 계정 재인증, A→B 전환, 세션 갱신/만료/401, 로그아웃·사본 정리. 실제 PostgREST 여행/날짜/장소 응답과 void RPC/에러 응답이 클라이언트 검증과 맞는지 확인한다.
2. **소유권과 우회 방지**: A/B 사용자 토큰과 anon으로 다른 여행/날짜/장소 읽기·쓰기, 직접 테이블 증가, 운영자 함수 호출·등급/관리자 조작이 거부되는지 확인한다. client owner/tier 값을 신뢰하지 않는지 검증한다.
3. **여러 연결 경쟁**: 마지막 한도 자리에서 동시에 여행 생성, 같은 여행 revision으로 날짜/장소 증가, 서로 다른 여행의 장소 증가, 정책/등급 변경과 생성 경쟁. 성공 개수·최종 revision·정책 적용 결과·교착 여부를 기록한다. 단일 연결 PGlite는 이 증거가 아니다.
4. **한도와 하향 보존**: free/paid1/paid2 초기 경계, 장소 한도, 정책 revision 충돌, 양의 정수 제약. 정책/등급 하향 후 기존 여행/날짜 편집은 보존되고 개수 증가만 해당 한도로 거부되는지 확인한다. 테스트 계정의 등급/관리자 설정만 변경한다.
5. **PC→Android**: PC의 두 여행·서로 다른 날짜 저장, Android 같은 계정에서 재열기. 두 여행/계정 내용이 섞이지 않는지 확인한다. Android에서 사본과 자체 앱 자원을 준비한 뒤 네트워크 차단·재실행·세션 만료 상태에서 열람/쓰기 금지, 미준비 여행, 저장 시각/revision, 재연결 최신성·입력 보존을 확인한다.
6. **실패 복구**: 서버 성공 후 조회/사본 실패, 응답 유실 뒤 최신본 확인·명시 확인, 불완전한 사본 교체, 삭제 실패·계정 전환 차단. 실제 서비스 확인과 제어한 실패 주입을 각각 표시한다.

## 완료 조건과 변경 금지

- 환경/계정 식별은 비밀 정보를 제외하고 기록한다. 각 사례의 실제 요청 종류·예상/실제 결과·잔여 미검증을 남긴다. 사용자 기기에서 실행했다면 안내와 사용자 결과를 대조한다.
- 발견한 T05 범위 결함만 재현·수정하고 필요한 테스트/빌드/CI, 문서 및 PR #7을 갱신한다. 구조 변경이나 계약 충돌은 고성능 Work에 넘긴다.
- 모든 필수 T05 완료 조건이 충족돼야 T05 완료와 T05A 인계를 제안한다. 이 Task 완료가 PR 병합 권한을 뜻하지 않는다. PR 갱신/검토 요청까지 수행하고 병합은 하지 않는다.
- 지도/검색/경로·T02 조사, 관리자 UI/T05A, 장소/일정 편집 UI/T06, 결제, 여행 삭제, 오프라인 쓰기, 사용자 데이터 변경/삭제, 공급자/플랫폼 변경은 금지한다.
