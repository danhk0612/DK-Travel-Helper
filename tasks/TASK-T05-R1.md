## 검토 결과와 수정 범위

검토 기준 코드는 `4cfe5a8`이다. 아래는 검토 당시의 결함과 수정 계약이다. `tests/browser.test.mjs`에 지연 응답·가상 계정·실패 저장소 회귀 사례를 추가했다. 이전 `cac037d`에서 계정 전환 노출과 지연 DB 열기 후 로그아웃 사본 부활을 재현했고 수정 후 통과했다. 실제 Google/Supabase 계정 없이 수행할 수 있다.

### 1. 계정 변경과 늦게 완료된 요청

초기 실행은 이전 계정 A의 사본을 `trips`에 넣고 OAuth 콜백 B를 저장한다. B의 목록 조회가 실패하면 A의 목록이 B 화면에 남는다. 이전 계정 사본을 삭제하는 콜백 전환 경로도 없다. `syncTrips`/`applyRemoteTrip`은 로그아웃 후에도 완료된 응답을 화면에 넣거나 IndexedDB에 다시 저장할 수 있다. 로그아웃 삭제 실패는 안내문만 띄우고 새 로그인을 허용한다.

- 계정 변경 전 A 화면·메모리 정리와 사본 삭제를 수행한다. 이전 계정 ID를 새 세션 저장 전에 확보한다.
- 요청/사본 작업을 현재 계정과 실행 세대에 귀속시키고 로그아웃·계정 전환 이후 오래된 완료 결과를 무시한다. 이미 시작한 사본 저장과 삭제의 순서도 보장해 삭제 후 부활하지 않게 한다.
- 삭제 실패 시 이전 계정 노출이 없어야 하며 정리가 확인되기 전 전환을 진행하지 않는다. 사용자에게 실패/재시도 상태를 제공한다.
- 세션이 없는 마지막 계정 사본 화면에서도 명시 로그아웃/사본 정리가 가능해야 한다.
- 검증: A 사본 + B OAuth 성공 + B 목록 실패, 지연된 A 응답 중 로그아웃, 지연된 사본 저장 중 로그아웃, 삭제 실패 후 새 로그인, 세션 만료 사본의 명시 정리.

### 2. OAuth 초기화와 세션 수명

`React.StrictMode`의 effect 재실행으로 `start`/PKCE 교환이 중복될 수 있다. `mounted`는 일부 setState만 막고 인증 교환·토큰 저장·`syncTrips`를 막지 않는다. refresh는 시작할 때만 수행하며 재연결에서는 온라인 표시만 바뀐다. 만료 세션의 쓰기 UI는 계속 활성화될 수 있다.

- OAuth 코드 교환/세션 초기화를 중복 실행에 안전하게 하고 인증 실패/재시도 흐름을 제공한다. 취소된 실행이 새 계정 상태를 덮어쓰지 않게 한다.
- 쓰기 전 유효 세션을 확인하고 갱신/인증 실패 시 준비된 사본 열람은 유지하되 재인증 전 쓰기를 막는다. 동시에 여러 요청이 refresh token을 경쟁 사용하지 않게 한다.
- 로그인 시작 실패도 사용자에게 표시하고 미처리 Promise rejection을 남기지 않는다.
- 검증: StrictMode 콜백 코드 교환 1회, 토큰 갱신 경쟁, 실행 중 만료/401, 오프라인 만료 후 재연결, 로그인 시작 실패.

### 3. 쓰기 결과가 불확실하거나 후속 읽기가 실패한 경우

여행 생성 RPC가 성공한 뒤 `loadTrip`/`syncTrips`가 실패하면 일반 실패 문구와 재생성 가능한 폼으로 돌아간다. RPC 응답만 끊긴 경우도 동일하게 처리해 사용자가 같은 여행을 다시 만들 수 있다. 날짜 저장 성공 이후 읽기 실패도 서버 성공과 구분되지 않는다.

- 확인된 RPC 성공과 후속 조회/사본 실패를 분리한다. 서버 성공을 실패로 취소하거나 재생성을 권하지 않는다.
- 응답 유실로 결과가 불확실하면 자동 재전송하지 않고 서버 최신본 확인·사용자 확인으로 복구한다. 이름만으로 같은 여행이라고 단정하지 않는다. 계약 밖 자동 병합/오프라인 큐를 추가하지 않는다.
- 성공 응답의 필수 ID/본문도 검증해 빈 응답을 저장 성공으로 처리하지 않는다.
- 검증: 서버 반영 후 RPC 응답 유실, RPC 성공 후 여행 읽기 실패, 날짜 저장 성공 후 읽기 실패, 복구 중 재제출 차단, 충돌 후 최신본 확인.

### 4. 사본 실패 격리와 형식

시작 시 `listSnapshots` 실패는 인증 초기화 전체를 중단한다. `syncTrips`의 사본 저장 실패는 조용히 무시된다. 사본에는 D003의 형식 버전이 없으며 T05의 장소 RPC로 만든 장소를 조회/사본에 포함하지 않아 완전한 여행 revision이라고 할 수 없다.

- IndexedDB 사용 불가여도 온라인 인증·서버 조회/저장이 가능하게 한다. 오프라인 준비 실패는 분명하게 표시한다.
- 사본 형식 버전·사용자·여행·revision·수신 시각을 검증하고 지원하지 않는 형식은 준비된 사본으로 표시하지 않는다.
- 현재 T05에서 서버에 저장 가능한 여행/날짜/장소 내용을 동일한 일관된 revision 조회와 원자적 사본에 포함한다. 장소 편집 UI/위치 공급자 필드는 추가하지 않는다.
- 열기/저장 오류를 처리하고 DB 연결은 성공/실패 모두 정리한다. 실패한 교체는 이전 완전본을 보존한다.
- 검증: IDB 열기/쓰기/삭제 실패, 중단된 교체, 다른 계정 필터, 형식 버전 불일치, 서버 장소 포함 사본 및 재열람.

### 5. 재연결·화면 복귀의 최신성

`online` 이벤트는 표시만 변경하고 최신 여행을 확인하지 않는다. `refreshSelected`는 조회 실패를 삼키며 동일 revision이면 '서버 저장'으로 표시한다. 변경 revision은 알림만 표시하지만 최신본 적용 시 입력 중인 날짜를 보호하는 명시적 흐름이 없다.

- 열기·재연결·화면 복귀·수동 확인에서 최신본을 조회한다. 사용자 입력이 있으면 자동으로 덮어쓰지 않고 현재/최신본 선택을 제공한다.
- 읽기 성공을 서버 쓰기 성공으로 표시하지 않는다. 오프라인 사본의 revision·수신 시각과 최신성 실패를 구분한다.
- 검증: 재연결 시 최신 revision, 날짜 입력 중 원격 변경, 조회 실패 시 이전 사본 유지, 수동 확인 시 목록/선택 여행 일치.

## 이미 수정한 SQL 결함

`v_trip.revision <> p_expected_revision`와 정책 revision 비교는 NULL 입력에서 조건이 true가 되지 않아 쓰기를 허용했다. 날짜·장소·정책의 비교를 `IS DISTINCT FROM`으로 변경했다. 초기 migration은 아직 main 미반영이다. 이미 개발 DB에 적용했다면 재실행으로 테이블을 덮어쓰지 말고 수정 함수 정의의 적용/전진 migration 절차를 준비한다. 실제 DB에 적용한 것으로 보고하지 않는다.

`tests/storage.test.mjs`는 PGlite PostgreSQL과 최소 Auth stub으로 NULL/오래된 revision, 기본 소유권, 직접 쓰기/운영자 호출 거부, 여행 개수 경계를 검사한다. 기존 코드에서 NULL revision 검사 2개 테스트가 실패했고 수정 후 3개 테스트가 통과했다. 단일 연결의 로컬 테스트로 실제 OAuth/PostgREST·여러 연결 잠금·Android 검증을 대신할 수 없다.

## 현재 구현과 검증 결과

- `src/data/workspace.ts`가 화면 상태·세션 적용·실행 세대·사본 쓰기/삭제 순서를 맡는다. `App.tsx`는 구독/입력/브라우저 이벤트를 연결한다. StrictMode에서도 초기화 1회, 계정 전환은 이전 ID 정리 후 새 세션 적용, 같은 계정 재인증은 사본 유지다.

- 여행·날짜·현재 서버 장소를 한 조회에 포함하고 형식 버전 1의 완전 사본을 원자적으로 저장한다. 이전 형식 없는 사본은 준비된 사본으로 표시하지 않으며 온라인에서 새로 준비한다.
